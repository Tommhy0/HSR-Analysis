# 崩铁伤害计算器（常规环境）

**新版深色工作台已完成。** 左侧分为角色与输出、增益管理、战斗情境、数据与来源，右侧集中展示结果。
新增可选择的情境增益及异相仲裁资料，数据库检查与剩余缺口见 [数据库检查与新版说明](数据库检查与新版说明.md)。
既有计算公式和逐条选择增益的方式继续保留；成品仍可双击离线使用。

**2026-10-13 审查修复已更新。** 十项修改、验证方式和剩余边界见
[审查修复记录](审查修复记录.md)。元素增伤现在填写局外总值（含行迹和属性球）；
扩散技能可切换主目标/相邻目标，后续伤害不会并入即时伤害。
下文的旧自检日志属于历史记录，当前结果以运行 `node _scripts/verify.mjs` 和 `node hsr_build.mjs` 为准。

选一个角色，算出它有伤害的技能在「自身的自拐 + 勾选的辅助增益 + 敌人的增减益 + 三深渊/异相 buff」
下打出多少伤害，并可选地判断这个数字在所选情境里算好还是差。

**辅助增益是逐条勾的，不是按角色选的。** 界面上是一份**增益目录**，
分三个页签（我方单体 / 我方全体 / 敌方负面），条目来自全部 6 类来源
（技能 / 忆灵技 / 行迹 / 星魂 / 光锥 / 遗器），**每条都把数值直接标出来**。
输出角色自己的自拐单独一张卡片，默认全勾。
这样「这条我算不算」是用户自己的决定，而不是「选了停云就等于一次性接受她身上所有增益」。

**排除范围**：货币战争 / 模拟宇宙 / 差分宇宙等特殊环境一律不算。**击破伤害与超击破伤害也不算**
（那是另一条公式链），相关技能会在界面上显式标注为「有意不算」，与「数据缺失」在界面上长得不一样。

技能下拉框里每一条都有**四档状态之一**，标记直接写在选项文字后面：

| 状态 | 标记 | 意思 |
|---|---|---|
| `ok` | （无） | 算得了 |
| `out-of-scope` | （v1 不算：击破伤害） | **我们有意不算** |
| `non-damage` | （不造成伤害） | **它本来就没有倍率这回事** |
| `unresolved` | （未收录倍率） | **我们没做到** —— 这才是要去补的 |

> **`non-damage` 这一档是补上去的，不是一开始就有。** 原来只有三档，全库 151 条
> `unresolved` 里 **126 条**根本不是伤害技能（布洛妮娅的战技、娜塔莎的治疗、艾丝妲的
> 终结技、杰帕德的盾），却被标成「未收录倍率」，告警文案还写着「需要人工补录进
> `annotations/multipliers.jsonl`」—— 那是**让人去补录一个不存在的东西**。
> 判据用的是 `tag` 在不在 `DAMAGE_TAGS` 里（与提取器同一个真相），**不是 `type`**；
> 且只在「一条倍率都没提出来」时判 —— tag 非伤害但确实提出了倍率的技能
> （阮•梅战技那种）照旧留在 `ok`，**25 条一条都没被误降级**。
>
> 现在的分布是 `ok 323 / non-damage 126 / unresolved 25 / out-of-scope 4`。
> `non-damage` 在界面上是**中性蓝**、走默认的黄边 notice —— 是说明，不是告警。
> 点「计算」它会直接说「这个技能不造成伤害，不参与计算」，**不会**掉进
> `core/damage.mjs` 那句「该技能没有可用的倍率（还没补录）」。
> 这四处文案（下拉标记 / badge / 头部计数 / `compute()` 短路）里
> **只有 `compute()` 那一处有自动断言**（反证 `R46` + 打包自检那一行），
> 其余三处是纯文案，DOM 打桩不解析 HTML —— **改错了不会变红，得自己看**。

## 怎么用

### 只想算伤害 —— 双击成品

双击 **`崩铁伤害计算器.html`** 就行。没有服务器、没有依赖、没有构建、不用联网。
数据（9 MB）是 gzip + base64 内嵌在文件里的，打开时用浏览器原生的 `DecompressionStream` 解回。

> 需要 Chrome 80+ / Edge 80+ / Firefox 113+。更老的浏览器会在页面上直接说「数据解压失败」
> 并讲清楚原因，**不会白屏**。

### 改了代码或标注 —— 跑开发服务器

双击 **`开发服务器.bat`**，然后开 <http://localhost:8777>。
开发期和成品跑的是**同一份** `ui/template.html`、**同一份** `ui/app.mjs`，差别只有「数据怎么塞进去」
这一件事 —— 所以不存在「开发能跑、打包就坏」。

### 重新打包

双击 **`打包单文件.bat`**。它会先自检再出成品：

```
模块加载 + 界面启动: OK
不打伤害的技能: 三月七 / 可爱即是正义（tag=Defence）→ 界面说「不造成伤害」，没掉进「还没补录」
端到端: 三月七 + 勾「姬子 · 秘技「不完全燃烧」」→ 918 伤害（基线 903），生效增益 6 条，可信度 unknown，2 处角色缺口 / 4 处辅助缺口
目录控件: 自拐 1 行 / 辅助 96 行（当前页签），两份不重叠；未列出 695 条（别家自拐 350 + 没装的光锥 244 + 遗器 101），合计 958 条
面板锚定条目: 10 个输入框，勾「布洛妮娅 · 终结技「贝洛伯格进行曲」」填 布洛妮娅的critDmg → 902 → 975 伤害；清空退回 902
全角色遍历: 97/97 算通
光锥命途过滤: 存护 16 把 / 全部 169 把；当前装备的命途不符那把仍旧列出
忆灵技: 12 条入表（8 个角色），其中 8 条可算、4 条显式标注算不了；长夜月一条端到端 9692 伤害
```

> 「不打伤害的技能」那行是**界面层唯一一条自动断言**：挑一条 tag 不是伤害标签的技能
> （三月七的护盾技）点下去，界面必须说「不造成伤害」。不说的话它会一路撞上
> `core/damage.mjs` 那句「该技能没有可用的倍率（还没补录）」——
> 把「这技能本来就不打伤害」说成「我们还没录」，正是这一轮要消灭的那种错标注。
> 反证里对应的 `R46` 把 `ui/app.mjs` 那段短路拆掉，这一行立刻变红。

这几行是**在 Node 里把打好的包真跑一遍**（DOM 打桩）得来的，不是「看起来没报错」。
它抓过两次真问题（模块拼接、渲染函数里的 ReferenceError）。

> 「光锥命途过滤」那行走的是**打包自检**（`cmd: 'hsr_build'`），不是 verify ——
> 命途过滤的产物**只出现在 `<option>` 里**，而 DOM 打桩不解析 HTML，数不出标记来。
> 所以这条规则被导出成 `S.lcList()`（自检问的是函数，不是渲染结果），
> 并把三件事一次钉死：只看本命途时只剩本命途的、「当前装备的那把**永远**在列表里」
> （去掉它，换角色后下拉框没有任何一项是 selected，浏览器默认显示第一项 ——
> 界面显示着一把光锥而 `st.lightconeId` 是另一把，**没有任何地方会报错**）、
> 关掉开关回到全部 169 把。反证 R51/R52/R53 分别打这三条。
>
> 「目录控件」那行里的**「未列出 695 条」是设计如此，不是漏了**：
> 别家角色的自拐（350）不该出现在你的辅助目录里，没装的光锥（244）和遗器套装（101）
> 同理 —— 它们的「装备者」不是当前角色。这 695 条加上列出的 263 条 = 958 条，
> 求和必须相等，自检里有断言盯着（少了就是分类漏了，多了就是把别人的自拐混进来了）。
>
> 「别家自拐」那一项从 326 涨到 350，涨的正是这次并进目录的忆灵辅助技。
> 25 条里 **20 条的 `target` 是「召唤者自己」**、3 条我方全体、2 条敌方负面。
> 而目录模型里**没有「忆灵」这一格** —— 它们的归属者记的是**召唤者**
> （昔涟德谬歌那 17 条记在昔涟名下）。这是一个**近似**，不是精确建模：
> 它让「算昔涟本人时能勾上自己忆灵给的增益」成立，代价是昔涟当队友时
> 那些条目按既有规则归入「别家自拐，不适用」。见下面那一节。
>
> 「面板锚定条目」那行走的是**另一条路**：勾了但不填面板 → 伤害不许变；
> 填上「布洛妮娅的暴击伤害」→ 伤害必须变大；把输入框**清空**（不是填 0）→
> 必须退回基线。三段少任何一段都能被糊弄过去 —— 只测中间那段的话，
> 一个「永远返回 0」的实现照样绿。

### 验证

```
node _scripts/verify.mjs          # 全库断言，纯 node，不碰浏览器
node _rev.mjs                     # 反证跑批：把每个机制故意改坏，确认对应断言真的会红
node hsr_build.mjs                # 打包，顺带跑一遍 DOM 打桩自检
node _scripts/coverage.mjs        # 非技能来源的覆盖率报表（技能已改走目录分桶）
node _scripts/review_buffs.mjs --report   # 看提取流水线攒下的待复核提案
```

**`verify.mjs` 的语义断言跑在「现场重跑提取器」的结果上，不是跑在烘好的缓存上。**
这是吃过一次亏才改的：忆灵技那批改动全在 `_scripts/extract_buffs.mjs` 里，
而全部断言原本读的是 `data.abilities`（构建期烧进 html 的旧结果）——
于是把基数归属规则整个改坏，verify **一条都不红**。现在分两层：
语义断言读现场重跑的结果，另有一条断言比对「现场重跑 === 烘焙产物」，
所以「改了提取器忘了重烘」也会红（那是静默的：页面照跑，跑的是旧数值）。

**本项目从不使用无头页面渲染做验证** —— 太慢，且抓不到数值错误。

│   ├─ sides.json               敌我侧种子表

├─ _scripts\  build_data / build_catalog / extract_buffs / review_buffs /
│             coverage / make_anchor / migrate_buff_ids / verify

**两条不可违反的架构约定：**

1. **运行期只读 `window.__HSR_DATA__`，从不 `fetch`。** 所以 `file://` 下的 CORS 问题从根上不存在。
   数据源不是文件，是构建期烧进 HTML 的一个块。
2. **`core/` 顶层不许出现 `node:fs` / `node:path` / `import.meta`。** 所有 IO 集中在
   `core/annotations.mjs`。这样同一个 `app.mjs` 才能在开发服务器和单文件成品里跑同一份。

## 它的数字可信在哪，不可信在哪

这是这个 README 最重要的一节。

### ✅ 能在库里对拍、已经对上的

| 项 | 状态 |
|---|---|
| 角色/光锥白值线性成长 | 三月七 L80 攻击 `236.64 + 3.48×79 = 511.56` |
| 敌方防御量纲 | `DEF = defence_base × defence_ratio × defence_modify_ratio`；`hlg=1` 时 `210 × ratio ≡ 200 + 10×等级`，**L=1..100 全中** |
| 星魂 R3/R5 的「技能等级 +2/+1」 | 只存在于 desc 散文（`param_list_json` R3/R5 是 97/97 全空），靠正则解析，有断言 |
| 三深渊敌人血量 | 按 `hp_formula_json.operands` 逐行反算，**7806/7806 吻合** |
| 占位符还原 | 全库 desc 还原后无 `#N`、无 `<unbreak>` 残留 |
| 忆灵生命上限 | `memosprite_json` 的 `hp_inherit` / `hp_base` 指进 `hp_skill` 的参数表，与 desc 原文**逐条对上**：阿格莱雅 ×66%+720 / 风堇 ×50% / 长夜月 ×50% / 昔涟 ×100% / 知更鸟•晴歌 ×70% / 开拓者 ×80%+640 |

### 🔴 对拍不了、必须靠你回填的

> **库里没有任何一列是游戏内实际打出的伤害。** 没有伤害日志，没有训练场记录。

所以上面那 451 条断言加起来，只能证明 **输入对、面板对、乘区自洽**，
**证明不了最终数字是对的**。

补救手段只有一个：**`_data_cache/anchors.json` 回填实测锚点。**

```
node _scripts/make_anchor.mjs 1001                # 列出这个角色哪些技能能算
node _scripts/make_anchor.mjs 1001 100101 --observed <游戏里打出的数> --append
node _scripts/verify.mjs                          # 看第 8 节
```

**没填锚点时，verify 第 8 节报 `SKIP`，不报 `PASS`。** 结尾会单独计数并写明
「跳过 ≠ 通过：上表里这些项从来没有被验证过」。SKIP 不进 `problems`、退出码仍是 0 ——
这是有意的：`anchors.json` 本来就是个可选输入，缺它就把整个脚本判失败会让人习惯性忽略失败。
但界面和结语里它**永远**不会被算进「通过」。

锚点失败时，verify 会把**每个乘区单独打出来**（基础 × 增伤 × 暴击 × 防御 × 抗性 × 易伤 × 击破 × 减伤），
所以一条锚点就能二分定位是谁偏了，而不是只说「总数不对」。

### 🔴 其它已知对拍不了的地方

| 项 | 说明 |
|---|---|
| 击破乘区 | 用的是社区公式（未击破 ×0.9）。库里没有可对拍的结算记录。界面上这一格**恒为红**。 |
| 抗性 clamp 边界 | 有结构化抗性数据，但边界取值没有实测对拍。 |
| 欢愉度基值 | 库内**不存在**。含欢愉度的技能显示「无法计算」，**不是 0**。 |
| 忆灵**自身**的攻击力 | `memosprite_json` 只有 `hp` 和 `speed`，**没有 atk**。阿格莱雅的衣匠、开拓者的迷迷那两条忆灵技吃的是忆灵自己的攻击力，所以**算不了**——界面上照旧列出来，标「倍率吃的是忆灵自己的攻击力」，**不拿召唤者的攻击力顶替**（社区有「忆灵继承召唤者 100% 攻击力」的说法，本项目没有采纳）。 |
| 忆灵技的实际档位 | 库里给的是 1–10 档的参数表，界面按**满档 10** 默认 —— 游戏内的实际档位规则本项目没有核实过，技能卡上写了「请自行核对」。 |
| 增益覆盖率 | 那是「我们录了多少」的度量，**不是「对不对」的度量**。 |
| 段数 | 只在散文里（366 个伤害技能里只有 21 条提到「额外造成 N 次伤害」）。界面上是显式输入字段，默认 1，`_trace` 里标 `assumed`。 |

## 增益覆盖度：现在到哪了

**口径已经换了：从「角色角标」变成「条目桶计数」。**

老口径给 97 个角色各发一个「未收录 / 部分 / 全」的角标。它被放弃，是因为它
答不上真正的问题：用户现在勾的是**条目**，不是角色 ——
「阮•梅是『部分』」并没有告诉他**哪一条能勾、哪一条不能**。
角色级角标还天然掩盖一类错误：一个角色身上有 11 条增益，录了 10 条漏了 1 条，
角标显示「部分」，看上去和「录了 1 条漏了 10 条」没什么区别。

现在报的是**分桶计数**。全库 1820 条来源文本切成 **3302 条含数值子句**，
每条子句必须落进且只落进下面一个桶（verify 第 9 节断言各桶之和 === 3302）：

| 桶 | 条数 | 进目录？ |
|---|---:|---|
| `PICKABLE` 可收录 | **918** | ✅ |
| `PANEL_ANCHORED` 数值取自**别人的面板**（见下面那段） | **11** | ✅（要填面板） |
| `TARGET_UNKNOWN` 认得出属性和侧别，但判不出作用于谁 | 38 | ❌ |
| `SIDE_UNKNOWN` 侧别判不出（**绝不默认我方**） | 3 | ❌ |
| `NO_ATTR` 影响伤害、有数值，但认不出属性键 | **148** | ❌ |
| `DOT_EXCLUDED` 有意不算：持续伤害 | 87 | ❌ |
| `BREAK_EXCLUDED` 有意不算：击破伤害 | 24 | ❌ |
| `EXTRA_INSTANCE` 有意不算：附加伤害（另一段） | 9 | ❌ |
| `NON_BUFF` 有数值但不是增益（治疗/段数/层数/阈值） | 480 | ❌ |
| `DURATION_ONLY` 纯时长/次数/回能，不影响伤害 | 985 | ❌ |
| `DAMAGE_TERM` 伤害倍率（归倍率流水线） | 599 | ❌ |

> **`NO_ATTR` 那 148 条就是「该补规则」的待办清单**，不是 bug。
> 桶里每一条的**原文都带得出来**（verify 断言：桶非空时样本列表必须非空），

### `PANEL_ANCHORED` 这一类是什么

「**提高数值等同于布洛妮娅#2%暴击伤害**+#3%的暴击伤害」—— 布洛妮娅、花火、
星期日的招牌战技全是这个形状。它们的数值 = **某个人的面板某一项 × 系数 + 平值**，
而那个人的面板计算器本来不知道：它是**队友**，你得自己填。

- 条目里带 `panel: { who, attr, flatParam, capParam }`；`who` 是面板归属者（显示名，
  或缺省 `@equipped` = 当前计算角色），`attr` 是面板字段名，
  `panel[p.attr] × paramIndex项 + flatParam项` 就是数值。
- **`who` 以 `@` 开头的是「伪归属者」**：它不是某个人名，而是界面上那份面板里的一格。
  `@equipped` = 当前计算角色（③ 里你填的那份面板）；
  `@energy` = **当前计算角色的能量上限**（角色固有属性，库里直给）。
  能量上限**不要**走 `@equipped`：它不是遗器词条，让用户手填只会填错。
  伪归属者的面板输入框不会多出来（它没有「是谁」可言），tooltip 里写「当前计算角色」。
- **`capParam` 是「最多计入 #N 点」**：基数先被**同一个来源里的另一项**夹住，
  数值 = `min(面板项, #N) × 系数`。漏掉这个夹子，能量上限 480 的角色会**静默偏高**
  （那两个上限 160 / 180 不是装饰）。`capParam` 取不到时**不夹** —— 取不到的
  是上限，不是数值本身。界面上这类条目的输入框说明会写「（含上限）」，
  悬浮提示补一句「先被同一句里的『最多计入』夹住」。
  verify 两边各钉一次：基数**超过**上限必须钉在上限、**低于**上限必须跟着基数走
  （只测一边的话，`base = cap` 这种写法能全绿）。反证 R49/R50 分别打这两边。
- **没填面板 ⇒ `catalogValue` 返回 `null`，不是 0。** 返回 0 的话这条会以
  「勾了、显示 0、伤害纹丝不动」的样子站在目录里，和「这条增益本来就没有」
  分不出来。现在它显示成「待填面板」，结果页的「勾了但没生效」清单
  会写明「请先填『布洛妮娅』的面板」。
- 界面上这类条目的行末多一个输入框（+「一键填充」，拿库里的白值 + 行迹算一份建议值）。
  同一个人的同**一项**只填一次，花火战技和花火 R6 共用。
- 这一类的**前身是一个 bug**：`NON_BUFF_RE` 里含「等同于」，整个家族被它一口吞掉，
  35 条子句连条数都数不出来。现在豁免由**顺序**承载（面板检查前置于那道闸门），
  `attr.mjs` 里仍然只有一份正则 —— 反证 `_rev.mjs` R32 盯的就是这个顺序。

#### 🔴 面板锚定的量**永远是平值**，哪怕句子里写着 `%`

用户报「刻律的技能有超大的 bug，伤害会偏高数万倍」。查下来是这一族：

「提高数值**等同于** X 的 #N%」说的是**增加量**等于 X 的那一面板项，
所以量纲跟着**基数**走，是一个**绝对值** —— `catalogValue` 那边也正是这么算的
（`面板[基数额] × pct + flat`）。但结果键常常落成 `atkPct` 这一档
（句尾写「的攻击力」、或紧邻那条写「攻击力提高」），于是这个绝对值被当成**百分比**
喂进 `inCombatPanel` 的 `out.atk * (1 + atkPct)`。

`FLAT_OF` 那一支**只认占位符后面没写 `%`** 的形态（`[i]` 是「点」、带 `%` 才是百分比），
而这一类的占位符后面**恰好都带 `%`** —— 整类漏掉了转换。

实测（刻律德菈 1412，满级白值 418.2）：

| | 修复前 | 修复后 |
|---|---:|---:|
| 她的天赋「持有【军功】的角色攻击力提高，提高数值等同于刻律德菈攻击力的 #2%」 | `atkPct = 100.4` → 攻击力 **42,387** | `atkFlat = 100.4` → 攻击力 **518.5** |
| 终结技「世事如棋，四步堪杀」（只算她自己） | 1,371,150 | 16,774 |
| 同上 + 知更鸟全部条目 | 8,382,446 | 38,741 |
| 同上 + 10 个来源整队 | 9,620,855 | 60,206 |

界面上也一直是错的，只是看不出来：`displayValueOf` 按 `/Flat$/.test(key)` 决定加不加
百分号，所以同一条以前显示 `+10036.2%`、现在显示 `+100.4`。

**受影响的 10 条**（键有 `FLAT_OF` 对应项的全部）：

| 条目 | 基数 | 修复前键 → 修复后键 |
|---|---|---|
| `1110.skill.111002.b1` 玲可 | 生命上限 | `hpPct` → `hpFlat` |
| `1110.rank.4.b2` 玲可 R4 | 生命上限 | `atkPct` → `atkFlat` |
| `1110.rank.6.b1` 玲可 R6 | 生命上限 | `hpPct` → `hpFlat` |
| `1205.rank.6.b2` 刃 R6 | 生命上限 | `hpPct` → `hpFlat` |
| `1208.skill.120802.b6` 符玄 | 生命上限 | `hpPct` → `hpFlat` |
| `1215.skill.121503.b1` 寒鸦 | 速度 | `speedPct` → `speedFlat` |
| `1309.skill.130903.b5` 知更鸟 | 攻击力 | `atkPct` → `atkFlat` |
| `1412.skill.141204.b1` 刻律德菈 | 攻击力 | `atkPct` → `atkFlat` |
| `1414.trace.1414101.b2` 丹恒•腾荒 | 攻击力 | `atkPct` → `atkFlat` |
| `1104.trace.1104103.b0` 杰帕德 | 防御力 | `atkPct` → `atkFlat` |

**没被误伤的**：基数是**百分比类**面板项（暴击伤害 / 击破特攻 / 效果命中）的那几条
（布洛妮娅、花火、星期日、忆灵迷迷、雪衣、黑天鹅、大丽花、开拓者•同谐）——
它们原本就是分数，`base × pct` 出来的就是分数，本来就对。逐条核过。

守这一族的是三条断言：原有的「平值键的句子里一定没有 %」**要排除掉带 `panel` 的条目**
（那条判据的前提是「`#N%` 就是产物本身」，而面板锚定条目的 `#N%` 是系数，
前提不成立）；新加的两条钉死「面板锚定条目的结果键不是 Pct 键」。
反证 R55 / R56 / R57 分别打「只转句内的」「丢了 `?? key`」「整段删掉」这三种修一半的做法。

#### `UNMODELLED`：模型里没有这一档的，显式置灰

同一族病还撞上一条：光锥「这就是我啦！」b2 写的是
「使装备者施放终结技时造成的**伤害值**提高，提高数值等同于装备者防御力的 #2%」。
关键在「伤害**值**」——它加的是**伤害的点数**（平值），不是伤害的百分比，
而 v1 的乘区里没有「平值伤害」这一档。`catalogValue` 算出来是 `防御力 × 0.6`，
存护角色防御力约 1500 → 900；这个数的量纲是「点」，但 `dmgBoost` 那一档要的是**分数**，
于是 900 被当成 +90000% 增伤 → 伤害 ×901。

于是加了 `core/catalog.mjs` 的 `UNMODELLED`：**逐 id 列出「算得了但算不对」的条目**，
`blockedReason` 里置灰，界面上值是「—」、悬停有长说明、结果页的清单里说
「模型里没有这一档（平值伤害），算不了」。
和 `piece_short` 同一套药方，区别在**补救动作**：一个去凑件数，一个根本没有补救动作。
verify 把这个名单**逐 id 钉死**（只数条数的话，往里多塞一条算得出来的就是**静默少算**，
而这正是这个项目最防的事），反证 R58 / R59 分别打「置灰失效」和「名单被塞宽」。

> 「今日亦是和平的一日」那两条**不受影响**：它们写的是「造成的伤害提高：
> 每点能量提高 #1%」，是**百分比**，而且 `#1[f2]` 的 0.002 本来就是「每点 0.2%」。
> 两条的差别就在「伤害**值**」那两个字上。

### 光锥那 10 条：被**分错桶**的伤害类增益

用户报「补全光锥带来的各种增益」。摸底之后补了 **10 条**，全部进 `annotations/buffs.jsonl`
（人工表），口径是**只补真正被分错桶的伤害类增益**，不扩到技能 / 行迹 / 星魂 / 遗器的同类问题。

「分错桶」的意思是：分类器**读到了这条子句**，但把它归到了某个不收录的桶
（`NON_BUFF` / `NO_ATTR` / `TARGET_UNKNOWN` / `SIDE_UNKNOWN`）。
它们和「判不出属性键」不是一回事，进的却是同一条救援通路。

补的时候有两条硬规矩，都不是格式问题：

- **`text` 必须逐字等于烘焙出来的原文**，差一个空格就触发 `humanMismatch`。
  这 10 条是**生成**的（从 `catalogSources` 里取 `buffClauseParts` 的同一段），不是手抄的。
- **参数项下标要对着 `skillParams` 数，不能对着中文句子数。** 已经踩过两次：
  `lc.24001.b1` 的 `#2` 是**敌方血量门槛**不是增益量（该取 `#3`）；
  `lc.21012.b1` 的 `#1` 是装备者自己的常驻增伤（该取 `#2`）。

**3 条刻意跳过，并在这里说明理由**（宁可漏算，不可算反）：

| 跳过 | 为什么 |
|---|---|
| `lc.21061` 假日浴场大冒险 b2 | 「有 `#2[i]%` **基础概率**使目标陷入易伤」—— `#2` 是**概率**不是伤害量。真正的易伤值在 b3，**已经在目录里**，收 b2 是重复计算。 |
| `lc.23052` b4 | 「【空白】和【诗行】的效果提高 `#4[i]%`」—— 它是**另外两个效果的放大器**，用任何一个单一属性键记都会重复计算。 |
| `lc.23053` 花花世界迷人眼 b5 | 「每消耗 1 个战技点使自身造成的**欢愉伤害**无视敌方 `#6[f1]%` 防御力」—— 欢愉命途角色的技能类型确实含 `Normal / BPSkill / Ultra / Talent`（实测 7 个欢愉角色全一样），所以一个全局的 `defIgnore` 会把「无视防御」**多算到普攻和战技上**（静默偏高）。 |

> 按属性键追一遍能看出这批补的是什么：`dmgBoost` / `abilityDmg`（限定技能类型）、
> `critRate`、`elemRes`。最后那个是**仅显示键** —— 抗性提高是**挨打那一侧**的减伤，
> 我方打出的伤害一点不变。它和 `speedPct` / `breakEffect` 同一档：
> 进目录是为了让这条子句有归属、在界面上看得见，**不进伤害公式**。

**「有意不算」和「数据缺失」在界面上长得不一样**，这是刻意的：
DoT / 击破 / 附加段 / 纯时长这四个桶是**我们知道自己不算**，用户看得见、也不必去补；
`NO_ATTR` / `TARGET_UNKNOWN` / `SIDE_UNKNOWN` 才是**我们没做到**。
把两者混成一个「未收录」数字，真警告会被假警告淹掉。

几条守着的口径：

- **判不出侧别绝不默认「我方」。** −60% 被当成 +60% 是方向性错误：
  数字变大、不报错、看着还挺合理。所以判不出就排除并列原文，verify 有断言盯着。
- `humanMismatch: 0` —— 人工表里那 77 条，每条的 id / 原文 / 属性键都和现烘的对得上。
  改了分类规则却忘了重烘，这里立刻报红。
  **这条比对只在分类器也给出了属性键时才做**：分类器判不出键（`byId` 的 key 为 null）
  的那些子句，人工表补上键**正是它唯一能被救回来的方式**，无条件比等于宣布
  「这些子句不许被人救回来」。保留的那半截仍守着真问题（键和语料对不上 → 算得出但算错），
  反证 R54 盯的就是它别被这次放宽顺手作废。
- 覆盖率仍然是「**我们录了多少**」，**不是「对不对」**。958 证明不了数值正确。
- **星魂不设门槛。** 任意星魂的增益都能直接勾，不受初始档位限制；
  基础档下 958 条里取得到值的有 934 条（差的 24 条全是带 `panel` 的 ——
  没填面板取不到值，其中 1 条是 `UNMODELLED` 有意置灰；实测确认过：
  不带 `panel` 却取不到值的一条都没有）。
  但 R3/R5 的「技能等级 +2/+1」**仍然跟随全局档位** —— 解锁只管「这条增益能不能勾」。
  `blockedReason` 里那条退役分支和 `displayValueOf` 的 `rank_locked` 分支**留着不删**，
  将来若再引入别的锁定，那条通路是现成的（`unmodelled` 就是照着这条路加进来的）。
  `blocked` 现有**两个**来源（`piece_short` 和 `unmodelled`），
  写「blocked 条数」的等式时**两边都要记** —— 且那条断言**必须带详情**，
  否则 `_rev.mjs` 读不出「哪条红了」，会报成「该红未红，这条断言是恒真的」。
- 非技能来源（行迹 / 星魂 / 光锥 / 遗器）走**自动路径**，结构化数值直接生效、不必手勾；
  技能增益才必须经目录勾选。这两条路**互斥** —— 同一条不会既自动生效又被勾一次，
  verify 有防重复计数的断言。

> 那 148 条的原文清单：`node _scripts/verify.mjs` 第 9 节，或
> `node _scripts/review_buffs.mjs --report`。非技能来源的覆盖率仍看
> `node _scripts/coverage.mjs`。

## 数据来源与口径

数据取自项目里已有的 4.5 数据库，构建期导出成 `_data_cache/hsr_core.json`。

- **面板由你直接填**，填的是**局外、未叠加任何增益的最终面板**。
  因此本项目**不做遗器模块**，也不需要主词条数值表（那张表库里本来就没有）。
  库里的白值只用来提供「一键填充初值」的便利，**你在界面上改过的值以你为准**。
- **标注表里永远不写数值，只写「数值从哪个数组的第几项取」。** 所以技能等级 / 叠影 /
  星魂 / 件数的联动全部自动成立，不会出现「改了等级但增益没跟着变」。
- **`value` 恒为正值，符号由属性键承载**（`1 + dmgBoost` / `1 - defShred`）。
  `direction` 只是文本极性记录，**不进数值**。

## 数据层里几个已知的脏点（显示层已经处理，**原始值没动**）

1. `abyss_floors.floor_name` 有 **80/708 行**含 `<unbreak>` 标签，其中 **21 条为空**。
   显示层 `scenario.mjs:displayName()` 负责剥标签并在为空时退回 id ——
   **只在显示这一层剥，原始值一个字节都没改。**
2. `monster_childs.stance_modify_value` 的 CamelCase 回退 —— 已确认**目前不是 bug**。
3. **角色名直接显示是挑不了的**，三个来源叠在一起：
   - 10 个开拓者（8001~8010）的 `name` 是字面的 `{NICKNAME}`。能区分它们的是
     `icon`（`playerboy` / `playergirl`，**带序号** —— 8003 是 `playerboy2`）。
   - 银狼LV.999（1506）的 `name` 带着 `<unbreak>` 标签（全库唯一一个）。
   - **三月七有两个**（1001 存护 / 1224 巡猎），底名一模一样。

   全部由 `ctx.mjs:characterDisplayName(ch, roster)` 处理，结果：
   `开拓者·存护（穹）` / `银狼LV.999` / `三月七（存护）`。
   verify 里有两条断言盯着它：**显示名不含标签或占位符**、**显示名互不重复**。
   > 这两条断言不是摆设 —— 加进去的当场就抓出了三月七重名和 8003~8010
   > 因为 icon 正则不带序号后缀而全部落空。
   > 注意 `roster` **必须传**，不传就没有重名信息，三月七那两条会长得一样。

4. **`abyss_seasons.version` 是整库快照的标签，不是每期的版本号。**
   那一列 92 行**逐字等于 `meta.version`**（全是 `4.5`），源数据里根本没有「这一期属于哪一版」。
   界面上原来直接显示它，于是**从 1.0 的第一期到最新一期全写着 v4.5** —— 这正是用户报的那个症状。

   现在版本号**由开始日期反推**：`scenario.mjs` 里有一张 30 个版本的上线日期表
   （`VERSION_STARTS`，1.0 ~ 4.5），`versionAt(begin)` 取「begin 那天所属的版本」。
   那个源字段仍在数据里（`snapshotVersion`），但**界面一处都不许用它**。

   几条守着它的口径：

   - **日期表本身要有人守。** 它的硬约束是「星期三 + 42 天」（2.1 之后逐条成立；
     1.0~1.6 是开服头一年，节奏没定型 —— 1.4→1.5 只有 35 天、2.0 还是星期二，
     那两段只查单调递增）。这些约束**共同**约束 30 个日期，不是恒真式。
   - **「期次 → 版本」另有 5 处绝对钉死**（`moc:1021 → 3.0`、`pf:2016 → 3.4`、
     `as:3006 → 3.0`、`moc:1016 → 2.3`、`as:3020 → 4.5`）—— 整张表平移、或者反推差一版，
     这 5 条立刻红。反证 R47/R48 分别打「读回快照标签」和「差一版」。
   - **92 期里只有 73 期反推得出版本**，另外 **19 期源数据根本没有 `begin_time`**
     （最早那批）。对它们 `versionAt` 返回 `null` —— 那是「不知道」，
     **不编一个 1.0 糊过去**，界面上就显示日期区间为「—」。
   - **每一期的 begin 都早于「下一版上线日」**，否则版本号与日期区间自相矛盾。
   - 版本号旁边一起显示**日期区间**（`2025-02-17 ~ 2025-03-31`），
     这样上面任何一条反推出了错，你自己看日期就能发现。

这三条都还等着裁定要不要改数据层。

### 忆灵（`memosprite_json`）：伤害侧 + 增益侧（记在召唤者名下）

**收录口径**：8 个角色有忆灵（阿格莱雅/衣匠、遐蝶/死龙•玻吕刻斯、风堇/小伊卡、
长夜月/长夜、昔涟/德谬歌、知更鸟•晴歌/晴空乐手、开拓者/迷迷 —— 就是全部有忆灵的角色）。
`memosprite_json.skills` 里共 53 条；挡掉 2 条 `desc` 为空的（遐蝶 `1140710/1140711`，
名字与 `1140702` 重复）之后，**按「打不打伤害」拆成两张表**：

| 表 | 条数 | 去向 |
|---|---:|---|
| `core.servantSkills` | **12** | 伤害侧：并进 `ctx.skillsByChar`，出现在技能下拉框里 |
| `core.servantSupport` | **39** | 增益侧：只进**增益目录**，不进技能下拉框 |

判据是 `tag` 在不在 `DAMAGE_TAGS` 里，**不是 `type`** —— 与提取器用的是同一份真相。

> **上一版把 39 条辅助技整个丢掉了**，理由是「它们根本没有倍率这回事」。那个理由
> 对**伤害下拉框**是成立的，但结论下过头了：它们是**增益**，本来就该走增益目录。
> 结果是昔涟德谬歌那 17 首诗一条都勾不到，「少技能」就是这么来的。
> 现在它们进目录，但**仍然不进技能下拉框** —— 把两张表合成一张的话，
> 昔涟的下拉框会从 7 条撑成 24 条，其中 17 条写着「未收录倍率」，
> 而那正是要消灭的错标注。

> **两张表都不收 `desc` 为空的**，所以 `skippedEmptyDesc` 记的是 2 而不是别的数。

**为什么必须分成两张表、不能合成一张加个 flag**：合起来得在**三个地方**各加一次过滤，
漏一处就是静默错 —— ① `ctx.skillsByChar` 会把技能下拉框撑爆（见上）；
② 提取器对忆灵的**第二遍**会给 Support 技也发**倍率提案**，撞掉
`attack_tag_unparsed === empty_desc` 这条划分不变量；
③ 打包自检要求 `data.servantSkills` 每条都出现在伤害下拉框里，而辅助技永远做不到。
拆开之后这三处**一行都不用改**。

**忆灵辅助技进目录是「记在召唤者名下」的近似。** 目录的来源角色模型里没有「忆灵」这一格：
25 条条目里 **20 条 `target` 是「召唤者自己」**、3 条我方全体、2 条敌方负面，
归属者一律记**召唤者**（昔涟德谬歌那 17 条记在昔涟名下）。所以它们出现在
**昔涟自己的自拐卡片**里，只在「算昔涟本人」时可选；昔涟当队友时按既有规则
归入「别家自拐，不适用」。这是**近似，不是精确建模**，不假装它是精确的。

**昔涟 17 首诗里进不来目录的那 5 首**（其余 12 首各进 1~3 条，共 17 条条目）：

| 诗 | 落桶 | 原因 |
|---|---|---|
| 此诗，献予一切生命（`1141502`） | `TARGET_UNKNOWN` | 「使其造成的伤害提高」的「其」指谁判不出 |
| 「你好，世界♪」（`1141505`） | —— | 整段**一个占位符都没有**，本来就没有含数值子句 |
| 献予「创世」之诗（`1141513`） | `TARGET_UNKNOWN` | 数值基数是**德谬歌自己**的生命上限 / 暴击率 |
| 献予「天空」之诗（`1141519`） | `NON_BUFF` | 回能 / 按治疗数值提高 —— 与伤害无关 |
| 献予「真我」之诗（`1141526`） | `DAMAGE_TERM` | 它本身就是伤害倍率句，属伤害侧 |

它们**不手工补录**，由既有的分桶报表覆盖（「未收录的增益按子句报、不按角色报」），
verify 第 7.7 节逐 id 钉死了各自落在哪个桶 —— 改分类规则时这几条会红。

**忆灵技的等级不吃星魂加成**：`effectiveSkillLevel` 按 `SKILL_TYPE_CN` 查表，
`Servant` / `ServantTalent` 两个键不在表里，所以原样返回基准等级。

**基数归谁是要判的**：提取器只看「`#N%` 后面跟什么属性词」，不看基数归谁 ——
「造成等同于「长夜」#1%生命上限」和「造成等同于遐蝶#1%生命上限」在它眼里一模一样。
把它们分开的是「占位符紧前面是谁的名字」这条规则：

| 原文 | 基数 |
|---|---|
| 紧前面是**召唤者**名（「等同于遐蝶#1%生命上限」） | 召唤者的（`hp`） |
| 紧前面是**忆灵**名（「等同于「长夜」#1%生命上限」） | 忆灵的（`servantHp`，需要折算） |
| **谁的名字都没有**（「造成#1%攻击力」） | 按 HSR 通用语义算忆灵自己的 |
| 「本场战斗…**累计治疗数值**」 | 不是面板项，算不了（`dynamicBase`） |

12 条逐条列在 verify 第 7.7 节里。这条规则判错的后果是伤害照常算得出、
界面上一切正常 —— 所以是逐条钉的，不是抽查。

## 下一步

**深做常用辅助的增益标注。** 这是整个项目唯一的人力瓶颈。
不过它的**目标已经变了**：以前是「把 56 个『未收录』角色的角标刷绿」，
现在是「**把那 148 条 `NO_ATTR` 的原文认出来**」——
也就是说，要补的是 `ATTR_RULES` 里的规则，而不是给每个角色手写一遍标注。
规则补一条，命中它的所有角色一起受益。流水线已经跑通：

```
node _scripts/review_buffs.mjs --report                # 分组统计 + 每桶样例
node _scripts/review_buffs.mjs --reason NO_SIDE        # 只看这一桶
node _scripts/review_buffs.mjs --show <id>             # 一条的全文与上下文
node _scripts/review_buffs.mjs --accept <id>           # 提升进 buffs.jsonl
node _scripts/review_buffs.mjs --reject <id> --why "…"
node _scripts/review_buffs.mjs --accept-reason OK      # 整桶提升（只许用于 OK / EXTRA_DAMAGE）
```

**`NO_SIDE` 桶必须逐条看** —— 它是「这条增益到底给我方还是给敌方」判不出来的那一类，
也正是把 −60% 算成 +60% 的唯一来源。其余桶（`OK` / `EXTRA_DAMAGE`）才可以整桶过。

`review_buffs.mjs` 是**纯 CLI，不开浏览器**。
